# 浪浪森友會 Constitution

## 核心原則

### I. CRM 為唯一事實來源

動物 CRM MUST 是所有動物基本資料、照護回報、歷史紀錄、照片、觀察訊號、人工覆核結果
與狀態異動的唯一事實來源。LINE Bot、LIFF、網頁後台、AI 模組與未來新增的輸入管道，
MUST 透過相同的後端服務與資料模型讀寫 CRM。任何模組 MUST NOT 建立無法與 CRM 對帳的
獨立業務資料副本；衍生摘要、分類、分數與快取 MUST 能由原始紀錄重新建立。此原則確保
所有介面讀寫一致，並讓資料可以重建與稽核。

### II. 原始資料不得被衍生結果取代

志工的原始文字、照片、表單值、建立者與建立時間 MUST 依資料保存政策保留。AI 摘要、
標籤及觀察訊號屬於衍生資料，MUST NOT 覆蓋或取代原始回報。所有摘要與觀察訊號 MUST
能追溯至原始紀錄。此原則保留現場證據，避免後續推論破壞資料可信度。

### III. AI 不負責計算、診斷或最終判定

AI MUST 僅用於從文字或照片擷取描述性資訊及產生建議值。AI MUST NOT 進行醫療診斷、
宣稱動物健康正常、計算關注分數、決定等級或排序、修改正式狀態、自動核准或拒絕，或
產生資料庫主鍵。分數、門檻、狀態、排序及最終決定 MUST 由可測試的程式規則或授權人員
執行。此原則將高風險決策留在可驗證且可負責的流程中。

### IV. AI 結果必須驗證、標示與追溯

所有 AI 輸出 MUST 經過結構驗證、白名單比對及禁用詞檢查。AI 結果在介面上 MUST 明確
標示，並保留模型版本、Prompt 版本、原始輸出及人工修正紀錄。需要寫入正式 CRM 欄位的
AI 建議值 MUST 先經授權人員確認。此原則使 AI 結果的來源、限制與人工作業責任清楚可查。

### V. 志工回填必須低摩擦

志工回報流程 MUST 以手機操作為優先，並以最少輸入、低學習成本及現場可完成為設計
目標。AI 處理 MUST 採非同步方式；AI 服務失敗時，原始回報仍 MUST 成功保存。不得為了
增加 AI 功能而增加不必要的志工操作。此原則優先保障現場回報率與原始資料完整性。

### VI. 歷史紀錄必須完整且可追溯

所有照護回報 MUST 以時間序列保存。系統 MUST 能顯示單一動物至少近 14 天的照護紀錄，
並保留更長期歷史查詢能力。同一動物同一天的多筆紀錄 MUST 併存，不得互相覆蓋。「沒有
回報」MUST 與「未偵測到明顯訊號」明確區分。此原則避免遺失事件，並支援連續照護判斷。

### VII. LINE Bot 只是輸入通道

LINE Bot 與 LIFF MUST 被視為 CRM 的輸入介面，不得承載核心業務規則或保存獨立狀態。
驗證、權限、冪等性、資料寫入、圖片處理及 AI 工作建立 MUST 在後端執行。LINE Webhook
MUST 具備簽章驗證與冪等處理。此原則讓通道可以替換，同時集中控制安全與資料一致性。

### VIII. 權限、隱私與稽核預設啟用

系統 MUST 遵循最小權限原則。私人照護紀錄、醫療資料、內部關注資訊及個人資料 MUST
依角色限制存取。重要資料異動 MUST 保留操作者、時間、變更內容及來源管道。公開資料
MUST 採白名單方式決定，不得預設公開內部資料。此原則將保護性控制設為預設，而非事後
補救措施。

### IX. P0 不得依賴 P1 或 P2

所有 P0 功能 MUST 能獨立完成、測試、展示與驗收。P0 的完成條件 MUST NOT 依賴任何 P1
或 P2 功能的輸出。外部服務或非核心功能失敗時，CRM 核心功能仍 MUST 可運作。此原則
確保核心交付具備可獨立驗收與可用的最小產品邊界。

### X. 文件語言一致性與 Python 品質門檻

所有供團隊閱讀的規格、計畫、任務、分析、測試及驗收報告 MUST 以台灣正體中文作為主要
敘事語言，使需求、決策、風險、結論與驗收結果可由正體中文讀者直接理解。程式碼識別字、
資料表、API 路徑、指令、套件名稱、檔案名稱、業界慣用術語、技術縮寫、產品或框架名稱，
以及 Spec Kit 工作流程標籤 MAY 保留英文，只要保留英文有助於精準表達、搜尋、工具對應或
跨文件一致性。

單一英文字詞、欄位標題或工作流程標籤，例如 `Spec outcome`、`Evidence`、`Setup`、
`Foundational`、`independent test`，MUST NOT 被單獨判定為違反本原則。同一份文件中的同一
概念 MUST 使用一致名稱；英文不得取代必要的中文脈絡，導致主要內容必須依賴整段翻譯才能
理解。審查者 MUST 依整份文件是否以正體中文清楚傳達主要資訊，而非依英文詞彙數量判定
合規。

Python 專案 MUST 使用 Ruff 管理格式化與靜態檢查，並使用 Pytest 驗證核心業務邏輯。
涉及 Python 的功能只有在下列指令全部通過後，才能標記為完成：

```bash
ruff check .
ruff format --check .
pytest
```

不得透過刪除測試、任意放寬 assertion、標記 skip 或大範圍停用 Ruff 規則來宣稱功能完成。
此原則讓文件、工具鏈與測試結果成為可重複檢驗的交付證據。

### XI. 多收容所資料隔離

本系統 MUST 支援多個動物收容所或中途機構共用同一平台，並將每個機構視為獨立的資料
租戶。所有非公開業務資料 MUST 明確歸屬至單一收容所或機構，至少包括使用者帳號、動物
資料、收容編號、日常照護回報、照片與心得、AI 擷取結果、醫療與照護紀錄、今日可回報
名單、QR Code、通知、稽核紀錄、規則與機構設定。收容編號只需在同一收容所內唯一；不同
收容所 MAY 使用相同收容編號，但所有查詢與正式資料關聯 MUST 同時受機構範圍限制。

除平台管理員執行明確授權且可稽核的跨機構管理作業外，任何使用者 MUST 只能讀取、建立、
修改或刪除其所屬或被明確授權機構的資料。A 收容所的管理員、工作人員或志工 MUST NOT
查看、搜尋、推測、修改或匯出 B 收容所的非公開資料。使用者提交的機構識別、動物識別、
收容編號或其他查詢條件 MUST NOT 被直接信任；系統 MUST 依已驗證的使用者身分重新判定其
可存取的機構範圍。

資料隔離 MUST 由後端及資料存取層強制執行，不得只依賴前端隱藏選單、網址或畫面。任何
跨機構資料存取需求 MUST 經明確授權、留下 Audit Log，且不得成為一般工作人員的預設能力。
此原則防止不同機構的資料因名稱、收容編號、查詢條件或使用者輸入相似而互相暴露，並使
跨機構作業具備可驗證的授權與責任邊界。

## 專案約束

規格、計畫、任務與決策紀錄 MUST 放置於專案既有的 Spec Kit 目錄。CRM 的正式資料模型與
後端服務 MUST 作為各輸入管道的共同依據。任何新增資料欄位、衍生資料、外部服務或 AI
流程 MUST 說明來源、保存政策、權限、失敗處理、重建方式與回滾或遷移方案。本機開發與
自動化 MUST 使用非正式環境的憑證與資料。

## 開發流程

工作 MUST 依序遵循：建立規格、規劃設計、產生可執行任務、實作任務、驗證結果。涉及 CRM、
AI 或 LINE 的變更，驗收條件 MUST 分別涵蓋資料來源、原始資料保存、權限、稽核、非同步
失敗處理與人工覆核邊界。P0 變更 MUST 提供獨立的測試、展示與驗收證據。審查者 MUST
拒絕超出規格範圍的工作，或要求拆分為獨立規格。任何例外 MUST 記錄理由、負責人、到期日
或後續工作，以及補償性驗證措施。

## 治理

本憲章是儲存庫的品質與資料治理標準。其他實務與本憲章衝突時，MUST 依本憲章處理，或
依開發流程記錄核准的例外。每份功能規格、計畫、合併請求與發布審查 MUST 檢查適用原則；
審查者 MAY 要求提供可驗證的資料來源、測試、稽核與人工覆核證據後才批准。

修訂 MUST 以儲存庫變更提出，並說明動機、對既有資料與工作的影響、遷移需求，以及需要
同步更新的模板或自動化。修訂只有在專案維護者審查通過，且同步更新版本、最後修訂日期
與同步影響報告後才生效。版本遵循語意化規則：重大治理不相容變更或原則移除／重新定義
使用 MAJOR；新增原則或實質擴充要求使用 MINOR；澄清與非語意文字修正使用 PATCH。

當新增功能流程、安全邊界、資料政策、AI 模型或發布流程時，專案 MUST 重新檢視本憲章。
合規缺口 MUST 記錄為可追蹤的後續工作或核准的例外，不得無聲忽略。
