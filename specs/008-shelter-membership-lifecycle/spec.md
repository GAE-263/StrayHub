# Feature Specification: 收容所成員封存與權限管理版型改善

**Feature Branch**: `008-shelter-membership-lifecycle`

**Created**: 2026-08-18

**Status**: Draft

**Input**: User description: "帳號可以封存，預設頁面資料收起來，使用者可透過額外 route 查詢；管理員與工作人員一區、志工獨立一區；改善排版；建立帳號使用 Modal。"

## Clarifications

### Session 2026-08-18

- Q: 已停用的帳號重新啟用時，應採用哪種規則？ → A: 一般停用成員可直接恢復為啟用中；志工若授權已過期或已撤銷，維持原授權狀態並不得繞過授權流程。
- Q: 志工授權被撤銷時，管理員清單應如何顯示？ → A: 帳號狀態與志工授權狀態分開顯示，卡片顯示「授權已撤銷」並使用偏灰色樣式。

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 封存與查詢收容所成員 (Priority: P1)

收容所管理員可以將不再使用的收容所成員封存，讓日常權限管理頁面只保留目前需要管理的成員；需要查詢歷史帳號時，可以進入獨立的已封存成員頁面並恢復成員權限。

**Why this priority**: 帳號持續累積會使管理員難以找到現役人員；封存必須同時解決清單過長與歷史資料保留問題。

**Independent Test**: 以 `local-shelter-admin-a` 登入，將一筆非目前操作者的 Membership 封存，確認它從 `/shelters` 的預設清單消失；進入 `/shelters/archived` 找到該成員，確認姓名、帳號、原角色與封存狀態可查詢，並能恢復。

**Acceptance Scenarios**:

1. **Given** 收容所存在啟用中的成員，**When** 管理員選擇封存，**Then** 系統顯示確認內容，成功後將該收容所的 Membership 標記為已封存並從預設清單隱藏。
2. **Given** 成員已封存，**When** 管理員開啟 `/shelters/archived`，**Then** 可以依姓名或帳號找到該成員，並看到角色、封存狀態與原有識別資訊。
3. **Given** 已封存成員仍保有照護回報或稽核歷史，**When** 管理員查詢相關歷史資料，**Then** 原始資料與操作者資訊仍可追溯，不因封存而刪除。
4. **Given** 已封存成員仍符合恢復條件，**When** 管理員選擇恢復，**Then** 成員回到日常權限管理清單，並依角色與有效期間恢復為適當狀態。
5. **Given** 成員在其他收容所仍有權限，**When** 管理員封存目前收容所的成員，**Then** 不影響該使用者在其他收容所的 Membership 或資料存取權。
6. **Given** 目前清單中的成員狀態為已停用，**When** 管理員選擇重新啟用，**Then** 一般成員恢復為啟用中；志工仍須依有效期間與授權狀態決定，不得繞過已過期或已撤銷的授權。

### User Story 2 - 分區檢視工作人員與志工 (Priority: P1)

收容所管理員查看權限管理頁面時，可以在上方「志工」區塊查看志工，在下方「工作人員」區塊管理收容所管理員與工作人員；兩區各自顯示筆數、空狀態與成員操作，避免所有角色混成一張過長清單。

**Why this priority**: 不同角色的管理目的與生命週期不同，分區能降低誤操作並讓管理員快速找到需要處理的對象。

**Independent Test**: 以包含 SHELTER_ADMIN、STAFF 與 VOLUNTEER 的收容所開啟 `/shelters`，確認志工在上方、工作人員在下方，且工作人員內管理員先於工作人員；每個成員的姓名、帳號、狀態與適用操作均可辨識。

**Acceptance Scenarios**:

1. **Given** 清單包含收容所管理員、工作人員與志工，**When** 管理員開啟權限管理頁面，**Then** 志工出現在上方「志工」，收容所管理員與工作人員出現在下方「工作人員」，且不在區塊標題後重複顯示角色名稱。
2. **Given** 某區塊沒有成員，**When** 管理員查看該區塊，**Then** 顯示清楚的空狀態與可用的後續操作，不留下空白或錯誤表格。
3. **Given** 成員為 STAFF，**When** 管理員查看該成員，**Then** 只在適用位置顯示醫療資料權限；志工區塊維持既有志工授權與有效期間語意。
4. **Given** 志工授權已撤銷，**When** 管理員查看志工卡片，**Then** 卡片顯示「授權已撤銷」並採偏灰色樣式，但不把授權狀態誤當成帳號封存或停用。

### User Story 3 - 使用清楚且響應式的管理版型 (Priority: P2)

收容所管理員在桌面、平板與手機寬度查看權限管理時，可以快速分辨頁面主要操作、分區、成員身份、狀態與次要操作；版型借鑑成熟管理後台的資訊層級，但維持本專案既有元件與視覺一致性。

**Why this priority**: 權限管理屬於高風險操作，清楚的視覺階層與足夠操作空間比單純塞入更多資料更重要。

**Independent Test**: 在 1440px、768px 與 360px 寬度開啟 `/shelters` 與 `/shelters/archived`，確認頁面沒有水平溢出或重疊，主要操作可在首屏找到，所有控制項都能操作。

**Acceptance Scenarios**:

1. **Given** 權限管理頁面已載入，**When** 管理員查看頁首，**Then** 可以在不滾動到底部的情況下找到建立帳號與已封存成員入口。
2. **Given** 成員清單包含多種狀態與角色，**When** 管理員查看任一成員，**Then** 姓名／帳號、狀態、權限與操作具有清楚的視覺分層與足夠間距；啟用中的卡片最清楚，停用、過期與撤銷的卡片採偏灰色處理。
3. **Given** 管理員使用 360px 寬度，**When** 查看或操作成員，**Then** 內容改以可讀的卡片或堆疊排列呈現，不需要水平捲動。

### User Story 4 - 以 Modal 建立帳號 (Priority: P2)

收容所管理員可以從權限管理頁面上方直接開啟建立帳號 Modal，填寫帳號、顯示名稱、暫時密碼與角色，成功後回到目前清單，不必滾動到頁面底部尋找表單。

**Why this priority**: 建立帳號是常用的主要操作，放在頁首能降低操作成本並避免表單被長清單推到頁面底部。

**Independent Test**: 以 `local-shelter-admin-a` 登入，從頁首開啟建立帳號 Modal，完成一次 STAFF 帳號建立；確認成功訊息、表單清空、Modal 關閉且新成員出現在工作人員區塊。

**Acceptance Scenarios**:

1. **Given** 目前收容所已啟用且管理員具備權限，**When** 管理員點擊建立帳號，**Then** Modal 顯示所有必要欄位與清楚的建立／取消操作。
2. **Given** Modal 已開啟，**When** 管理員按 Escape、關閉按鈕或取消，**Then** Modal 關閉且不建立帳號；再次開啟時不保留未提交的敏感密碼。
3. **Given** 管理員送出不完整或重複帳號，**When** 後端拒絕建立，**Then** Modal 保持開啟、顯示可理解的錯誤訊息，並保留非敏感欄位供修正。
4. **Given** 帳號建立成功，**When** Modal 關閉，**Then** 清單重新載入並保留既有權限、稽核與志工授權邊界。

### Edge Cases

- 管理員不得封存自己目前使用的 Membership。
- 系統不得讓封存動作造成收容所沒有任何可用的 SHELTER_ADMIN；若只剩一名管理員，應拒絕並說明原因。
- 封存操作重複送出或成員已被其他視窗修改時，系統應回報目前狀態並重新整理清單，不得錯誤覆寫。
- 已封存成員的使用者資料缺少姓名或帳號時，仍使用安全的未命名提示，不以 UUID 作為主要名稱。
- 志工的有效期間已過時，恢復封存不得將其錯誤變成永久啟用；應維持已過期或依既有志工授權流程處理。
- 已停用成員重新啟用時，系統必須保留操作者與時間的稽核紀錄；志工授權已過期或已撤銷時，不得直接恢復為可用狀態。
- 志工授權撤銷只代表該志工授權不再有效，不等同於 Membership 封存或帳號停用；清單仍須顯示該成員的可追溯資訊。
- `/shelters/archived` 必須遵守目前收容所權限範圍，不能查到其他收容所的封存資料。
- 建立帳號 Modal 在手機寬度下不得被視窗裁切，密碼欄位不得出現在錯誤訊息或成功通知中。

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: 權限管理頁面 MUST 提供「封存」操作，封存目前收容所的 Membership，而不是刪除 User、照護回報、稽核或其他歷史資料。
- **FR-002**: 封存成員 MUST 從 `/shelters` 的預設可管理清單隱藏，且頁面 MUST 提供前往 `/shelters/archived` 的入口。
- **FR-003**: `/shelters/archived` MUST 僅顯示目前已驗證收容所範圍內的封存成員，並提供姓名／帳號查詢、角色與封存狀態檢視。
- **FR-004**: 管理員 MUST 能從已封存成員頁面恢復成員；恢復結果 MUST 依角色、有效期間與既有志工授權規則決定可用狀態。
- **FR-004a**: 管理員 MUST 能將目前清單中的已停用 Membership 重新啟用；一般成員 MUST 恢復為 `active`，志工若授權已過期或已撤銷則 MUST 維持對應狀態，不得藉由重新啟用繞過志工授權流程。
- **FR-005**: 封存與恢復 MUST 保留操作者、時間、目標 Membership 與結果的 Audit Log，並維持既有跨收容所隔離。
- **FR-006**: 系統 MUST 防止管理員封存自己，且 MUST 防止封存後收容所沒有可用 SHELTER_ADMIN。
- **FR-007**: 權限管理頁面 MUST 將 VOLUNTEER 放在上方「志工」區塊，將 SHELTER_ADMIN 與 STAFF 放在下方「工作人員」區塊；區塊標題後不得重複顯示「收容所管理員」或「工作人員」角色名稱，封存頁面也 MUST 維持相同分區。
- **FR-008**: 每個角色區塊 MUST 顯示成員數量、清楚的空狀態，以及與該角色適用的操作；非 STAFF 不得顯示醫療資料權限控制；啟用中、停用、過期與撤銷狀態 MUST 使用可辨識且一致的視覺樣式。
- **FR-009**: `/shelters` 與 `/shelters/archived` MUST 在 1440px、768px 與 360px 寬度下避免水平溢出、文字重疊與不可操作的控制項。
- **FR-010**: 權限管理頁面首屏 MUST 提供建立帳號與已封存成員入口，不得要求管理員滾動至清單底部才能開始建立帳號。
- **FR-011**: 建立帳號 MUST 使用 Modal，包含帳號、顯示名稱、暫時密碼與角色欄位，並支援取消、Escape、關閉、驗證錯誤與成功後重新載入。
- **FR-012**: 建立帳號失敗時 MUST 保留非敏感欄位、清除或不保存密碼，並顯示不洩漏內部實作細節的錯誤訊息。
- **FR-013**: 既有角色調整、醫療資料權限切換、停用操作、志工授權流程與稽核行為 MUST 維持原有授權邊界與結果。
- **FR-014**: 所有成員姓名、帳號、狀態與封存資料 MUST 受目前已驗證的收容所管理範圍限制，不得因查詢或顯示需求洩漏其他收容所資料。
- **FR-015**: 一般清單與封存清單的區塊順序 MUST 為「志工」在上、「工作人員」在下；工作人員區塊內 MUST 先排列 SHELTER_ADMIN，再排列 STAFF；各區塊內狀態順序 MUST 為啟用中、已停用、已過期，志工授權撤銷的項目排在已過期之後。
- **FR-016**: 志工授權撤銷 MUST 以「授權已撤銷」呈現，並與 Membership 的停用、封存狀態分開；撤銷卡片 MUST 使用偏灰色視覺，不得讓管理員誤認為可透過重新啟用帳號恢復授權。

### Key Entities _(include if feature involves data)_

- **使用者**：全平台登入主體；封存某一收容所的 Membership 不得自動影響其在其他收容所的 Membership。
- **Membership**：使用者與收容所的角色關聯；新增封存生命週期狀態，保留角色、有效期間、醫療資料權限與歷史關聯。
- **已封存成員檢視**：管理員查詢目前收容所封存 Membership 的獨立入口，包含搜尋、分區、狀態與恢復操作。
- **稽核紀錄**：封存、恢復、建立與既有權限異動的可追溯紀錄。

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 管理員封存一筆成員後，該成員在 1 次清單重新載入內從 `/shelters` 消失，且能在 `/shelters/archived` 找到並辨識。
- **SC-002**: `/shelters` 預設清單不顯示任何已封存成員；已封存頁面可查詢 100% 的目前收容所封存成員，且不顯示其他收容所資料。
- **SC-003**: 在 1440px、768px 與 360px 寬度下，100% 的角色區塊與成員項目沒有水平溢出、文字重疊或不可操作控制項。
- **SC-004**: 管理員從頁面首屏開啟建立帳號 Modal 的操作不需頁面捲動，成功建立帳號的流程可在 2 分鐘內完成。
- **SC-005**: 封存、恢復、建立帳號、角色調整與醫療資料權限切換的成功與拒絕結果均保留可追溯的操作者與時間資訊。
- **SC-006**: 封存與恢復測試涵蓋管理員、工作人員、志工、其他收容所 Membership 與志工有效期間，既有使用者資料與歷史回報均不被刪除。
- **SC-007**: 在一般與封存清單中，100% 的成員依指定區塊、角色與狀態順序呈現；啟用中的卡片與停用、過期、撤銷卡片可由視覺樣式直接區分。

## Assumptions

- 預設 `/shelters` 只顯示未封存且仍屬於目前收容所的 Membership；過期或撤銷的志工若未封存，仍依既有規則顯示在志工區塊。
- 「帳號封存」在本功能以目前收容所的 Membership 封存為主，不直接刪除全平台 User，避免影響其他收容所與歷史資料。
- `/shelters/archived` 是管理員可進入的額外管理路由，使用與 `/shelters` 相同的收容所範圍與授權邊界。
- 永久刪除 User 不在本功能範圍內；若未來需要，應另立規格處理資料保存、引用關係與稽核要求。
- 版型只借鑑成熟管理後台的資訊階層與響應式模式，沿用專案既有 UI 元件，不直接引入整套外部模板或改寫其他管理頁。
- 志工的「已撤銷」指志工授權已被撤回，不代表全平台 User 或目前收容所 Membership 被刪除；該狀態需保留查詢與稽核能力。
