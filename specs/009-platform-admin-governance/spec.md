# Feature Specification: 平台管理員人數與替換治理

**Feature Branch**: `[009-platform-admin-governance]`

**Created**: 2026-08-18

**Status**: Completed — 56/56 項任務已完成；T055–T056 remediation 已實作並驗證

**Input**: User description: "平台管理員至少保留一位、正常最多兩位；需要建立平台管理員的新增、停用、替換與稽核流程。"

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 維持平台管理員安全下限 (Priority: P1)

平台管理員需要能管理平台管理員名單，但系統必須始終保留至少一位啟用中的平台管理員，避免最後一位管理員被停用或降權後平台失去治理能力。

**Why this priority**: 這是平台治理的基本安全條件；若沒有可用的平台管理員，後續帳號、收容所與權限管理都可能無法進行。

**Independent Test**: 建立只有一位啟用中平台管理員的情境，嘗試停用或降權該帳號，確認操作被拒絕且原帳號仍可登入與管理平台。

**Acceptance Scenarios**:

1. **Given** 平台目前只有一位啟用中的平台管理員，**When** 操作者嘗試停用或降權該平台管理員，**Then** 系統拒絕操作並說明至少須保留一位啟用中的平台管理員。
2. **Given** 平台有兩位啟用中的平台管理員，**When** 其中一位停用或降權，**Then** 系統允許操作，且另一位仍保有平台管理員權限。
3. **Given** 平台管理員異動請求同時發生，**When** 多個操作可能使啟用中的平台管理員數量變成零，**Then** 系統只接受不違反下限的結果，不產生短暫或最終的零位狀態。

### User Story 2 - 控制平台管理員正常上限 (Priority: P1)

平台管理員需要新增或提升帳號權限，但一般情況下平台只保留最多兩位啟用中的平台管理員，降低高權限帳號暴露與誤操作風險。

**Why this priority**: 平台管理員具備跨收容所的高權限；明確的正常上限可控制權限面積，同時保留雙人治理與交接能力。

**Independent Test**: 建立兩位啟用中的平台管理員後，嘗試新增或提升第三位，確認操作被拒絕，且既有兩位與目標帳號狀態不變。

**Acceptance Scenarios**:

1. **Given** 平台已有兩位啟用中的平台管理員，**When** 操作者嘗試新增或提升第三位平台管理員，**Then** 系統拒絕操作並引導使用替換流程。
2. **Given** 平台有一位啟用中的平台管理員，**When** 操作者提升另一位符合條件的帳號，**Then** 系統完成提升，平台共有兩位啟用中的平台管理員。
3. **Given** 目標帳號已是平台管理員但目前停用，**When** 操作者嘗試直接重新啟用且啟用後不超過兩位，**Then** 系統依既有帳號狀態規則處理，並重新確認人數上下限。

### User Story 3 - 以替換流程完成管理員交接 (Priority: P1)

平台管理員需要在達到兩位上限時交接職責，因此可以先指定一位符合條件的新管理員，再在同一個確認流程中撤銷原管理員的高權限，完成不超過兩位且不低於一位的替換。

**Why this priority**: 沒有替換流程時，兩位管理員無法安全輪替；若先停用舊管理員又無法新增新管理員，容易造成平台失去治理能力。

**Independent Test**: 以兩位啟用中的平台管理員開始，指定一位非平台管理員的啟用帳號作為替代者，完成替換後確認新帳號成為平台管理員、原帳號不再具備平台管理員權限，且平台仍恰有兩位啟用中的平台管理員。

**Acceptance Scenarios**:

1. **Given** 平台已有兩位啟用中的平台管理員，**When** 操作者選擇一位符合條件的替代帳號並確認替換，**Then** 系統完成新舊權限交接，平台管理員數量維持兩位。
2. **Given** 替代帳號不存在、已停用、已具備平台管理員角色或不符合帳號安全條件，**When** 操作者提交替換，**Then** 系統拒絕整個操作，既有平台管理員權限不變。
3. **Given** 替換流程在完成前發生失敗，**When** 系統回報錯誤，**Then** 不得只完成部分權限異動，操作者可重新檢視目前狀態後再試。
4. **Given** 替換成功，**When** 任一授權使用者查看平台管理員異動紀錄，**Then** 可辨識操作者、時間、替代者、原管理員、變更前後狀態與操作結果。

### Edge Cases

- 最後一位啟用中的平台管理員嘗試自行停用或降權時，操作必須被拒絕。
- 兩位平台管理員同時提升不同帳號時，最多只能有兩位啟用中的平台管理員成功；被拒絕的操作不得留下部分權限或成功稽核紀錄。
- 替換目標在確認後、完成前已被停用或取得平台管理員角色時，替換必須失敗並保留原管理員權限。
- 已停用或已撤銷平台管理員權限的帳號不計入啟用中的平台管理員數量，但不能被直接視為仍具備平台管理權限。
- 平台管理員帳號不應因收容所 Membership 的角色變更而取得或失去平台層級權限；兩種權限範圍必須分開判定。
- 任何拒絕操作都不得洩漏其他收容所或不具權限帳號的非必要資料。

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: 系統 MUST 將平台管理員視為平台層級權限，不以任何單一收容所 Membership 取代平台管理員身分判定。
- **FR-002**: 系統 MUST 只將狀態為啟用且具平台管理員權限的帳號計入平台管理員人數。
- **FR-003**: 系統 MUST 維持至少一位啟用中的平台管理員。
- **FR-004**: 系統 MUST 將兩位啟用中的平台管理員設定為正常上限。
- **FR-005**: 系統 MUST 在新增或提升平台管理員前重新確認人數上限；若已達兩位， MUST 拒絕一般新增或提升操作並提供替換流程入口。
- **FR-006**: 系統 MUST 在停用或降權平台管理員前重新確認人數下限；若操作會使人數低於一位， MUST 拒絕操作。
- **FR-007**: 系統 MUST 提供平台管理員替換流程，讓授權操作者以一次確認完成符合條件的新帳號提升與原平台管理員降權，並確保結果同時符合上下限。
- **FR-008**: 系統 MUST 在替換前確認新帳號為啟用狀態、尚未具備平台管理員角色且符合既有帳號安全條件；任一條件不符時 MUST 拒絕整個替換操作。
- **FR-009**: 系統 MUST 確保平台管理員新增、提升、啟用、停用、降權與替換不會產生只完成一半的權限狀態。
- **FR-010**: 系統 MUST 以後端授權重新驗證操作者、目標帳號及最新平台管理員數量，不得只依賴畫面上的按鈕狀態。
- **FR-011**: 系統 MUST 為每次成功或拒絕的平台管理員異動保留稽核紀錄，至少包含操作者、時間、目標帳號、變更前後狀態、操作類型、結果與拒絕原因（如有）。
- **FR-012**: 系統 MUST 讓平台管理員能清楚辨識目前啟用中的管理員、已停用的平台管理員、平台權限已撤銷的歷史異動，以及目前人數與可用名額；平台權限已撤銷的帳號不得被誤列為目前平台管理員。
- **FR-013**: 系統 MUST 對可能同時發生的管理員異動維持一致的人數結果，不得因競爭操作突破兩位上限或低於一位下限。
- **FR-014**: 系統 MUST 保留既有收容所 Membership 角色與平台管理員角色的獨立性；修改其中一種角色不得未經明確授權連帶修改另一種角色。
- **FR-015**: 系統 MUST 將具有 `VOLUNTEER` Membership 或志工申請紀錄的帳號排除於「提升既有帳號」候選清單，且後端 MUST 拒絕直接將志工帳號提升或替換為平台管理員。

### Key Entities _(include if feature involves data)_

- **平台管理員身分**：代表使用者是否具有平台層級管理權限，以及該權限目前是否啟用。
- **平台管理員治理政策**：代表啟用中平台管理員的最小數量一位與正常最大數量兩位，以及替換流程適用條件。
- **平台管理員異動紀錄**：記錄平台管理員權限新增、提升、啟用、停用、降權與替換的操作者、時間、範圍、前後狀態與結果。
- **使用者帳號**：作為平台管理員身分與收容所 Membership 的共同使用者資料，但兩種授權範圍分開管理。

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 在所有成功完成的平台管理員異動後，啟用中的平台管理員數量 100% 落在一至兩位之間。
- **SC-002**: 最後一位啟用中的平台管理員執行停用或降權時，100% 被拒絕且不改變其有效權限。
- **SC-003**: 已達兩位啟用中的平台管理員時，第三位的一般新增或提升操作 100% 被拒絕，且既有兩位權限不受影響。
- **SC-004**: 使用替換流程時，所有成功測試案例都必須在一次確認後完成新舊管理員交接，且不需先暫時降低平台管理能力。
- **SC-005**: 每次成功或拒絕的平台管理員異動都有完整稽核紀錄，完整欄位覆蓋率達 100%。
- **SC-006**: 使用 quickstart 定義的 Standard Local Fixture（2 位平台管理員、1 個可提升帳號、3 位具有不同 Membership 歷史的帳號、3 位具有不同 VolunteerApplication 歷史的帳號）時，管理者在 5 次驗收中至少 4 次能於 30 秒內辨識目前啟用中的平台管理員人數、剩餘名額與可執行的新增或替換操作。
- **SC-007**: 平台管理員與收容所 Membership 角色的權限異動驗收中，100% 的測試案例維持兩種角色範圍獨立。

## Assumptions

- 平台管理員是平台層級角色，不需要透過建立或保留任何收容所 Membership 才能生效。
- 「最多兩位」是正常營運上限；本 Feature 不提供未經稽核的第三位常態平台管理員，也不設計緊急繞過機制。
- 替換流程的授權操作者為目前啟用中的平台管理員；其他角色不得管理平台管理員身分。
- 帳號密碼、登入狀態與既有帳號停用規則沿用現行機制，本 Feature 只定義平台管理員治理邊界。
- 本 Feature 不提供平台管理員封存、硬刪除或移除 User；降權會清除平台角色，但保留 User、Membership、Session 與 AuditRecord 歷史。
- 既有稽核能力可保存平台管理員異動；若現有稽核欄位不足，實作規劃階段必須補足而不建立第二套無法對帳的紀錄來源。
- 本 Feature 不處理平台管理員以外的 STAFF、SHELTER_ADMIN 或 VOLUNTEER 人數限制。
- 志工帳號仍可保留 User、Membership 與申請歷史；本 Feature 不提供志工直接轉任平台管理員流程。
## Account security conditions

- 新建或提升為平台管理員的帳號，必須符合既有帳號安全規則：帳號名稱不可為空、必須唯一，且 User 狀態必須為啟用中。
- 替代平台管理員的目標帳號不得已具有 `PLATFORM_ADMIN` 角色；同一帳號不可重複占用平台管理員名額。
- 新建帳號使用的暫時密碼必須符合現行密碼政策，並且不得以明文保存。

## Migration and bootstrap conditions

- Migration 建立平台管理員政策單例後，須檢查既有資料庫中的啟用中平台管理員數量。
- 對已有 User 資料的環境，若啟用中平台管理員數量為 0 或超過 2，Migration 必須失敗並提供可操作的修復提示，避免系統以不符合政策的狀態啟動。
- 全新空資料庫可先完成 Migration，但服務正式啟動前，bootstrap 或 seed 流程必須建立至少一名啟用中的平台管理員。
