# Feature Specification: 收容所管理員人數與權限調整確認

**Feature Branch**: `[010-shelter-admin-governance-confirmation]`

**Created**: 2026-08-18

**Status**: Draft

**Input**: User description: "收容所管理員的權限也是每個收容所至少一個、最多兩個；管理員調整權限時，先用 Modal 再確認一次，完成修改後在左下角顯示 Toast，讓管理員知道完成了什麼權限調整動作。"

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 維持每個收容所的管理員人數邊界 (Priority: P1)

收容所管理員調整成員角色或帳號狀態時，系統會維持該收容所至少一位、最多兩位啟用中的 `SHELTER_ADMIN`，避免收容所失去管理能力，也避免高權限帳號過度增加。

**Why this priority**: 人數下限是收容所持續營運的必要條件，上限則是降低高權限暴露面的基本治理控制；兩者都必須在每次權限異動時成立。

**Independent Test**: 建立一個只有一位啟用中收容所管理員的收容所，嘗試停用、降權或封存該管理員；再建立兩位啟用中管理員，嘗試新增、提升或重新啟用第三位，確認兩類操作都被拒絕且既有權限不變。

**Acceptance Scenarios**:

1. **Given** 收容所只有一位啟用中的 `SHELTER_ADMIN`，**When** 管理員嘗試停用、降權或封存該帳號，**Then** 系統拒絕操作，說明至少須保留一位啟用中的收容所管理員，且目標帳號權限不變。
2. **Given** 收容所已有兩位啟用中的 `SHELTER_ADMIN`，**When** 管理員嘗試新增、提升或重新啟用第三位，**Then** 系統拒絕操作，說明已達兩位上限，且既有帳號與目標帳號狀態不變。
3. **Given** 收容所只有一位啟用中的 `SHELTER_ADMIN`，**When** 管理員將另一個符合條件的成員提升為管理員，**Then** 系統完成異動，啟用中的收容所管理員數量變成兩位。
4. **Given** 收容所已有兩位啟用中的 `SHELTER_ADMIN`，**When** 管理員先讓其中一位離開啟用狀態後再提升其他成員，**Then** 每個成功結果仍維持一至兩位啟用中的管理員，且不允許任何一步造成零位或三位狀態。

### User Story 2 - 以確認 Modal 防止誤改權限 (Priority: P1)

收容所管理員調整既有成員的角色、啟用狀態、醫療資料權限或志工授權時，系統會先顯示確認 Modal，讓操作者核對收容所、目標成員、目前權限、即將變更的權限，以及人數限制的影響，再決定是否完成異動。

**Why this priority**: 權限異動會直接影響資料可見範圍與工作能力；在提交前提供明確確認可降低誤按，也讓人數上下限的風險可被看見。

**Independent Test**: 以收容所管理員登入，對一名工作人員執行角色或醫療資料權限調整；確認 Modal 顯示完整前後差異，選擇取消或關閉後資料不變，重新操作並確認後才完成變更。

**Acceptance Scenarios**:

1. **Given** 管理員在權限管理頁面選擇一項有效權限異動，**When** 管理員按下操作按鈕，**Then** 系統先顯示確認 Modal，不直接提交變更。
2. **Given** 確認 Modal 已開啟，**When** 管理員查看內容，**Then** 可以辨識收容所名稱、目標成員的姓名或帳號、目前角色／狀態、變更後角色／狀態，以及是否影響管理員人數或其他權限。
3. **Given** 確認 Modal 已開啟，**When** 管理員按取消、關閉或 Escape，**Then** Modal 關閉、權限資料不變，也不產生成功通知。
4. **Given** 確認 Modal 已開啟，**When** 管理員確認變更且後端驗證成功，**Then** 系統只完成一次權限異動，更新清單並顯示成功 Toast。
5. **Given** 確認 Modal 已開啟，**When** 人數限制、授權或目標狀態檢查失敗，**Then** 系統不改變任何權限、不顯示成功 Toast，並提供可理解的失敗原因與目前狀態。

### User Story 3 - 透過 Toast 確認完成的權限動作 (Priority: P2)

收容所管理員完成權限異動後，可以在頁面左下角看到短暫且清楚的 Toast，知道哪一位成員完成了哪一項權限調整；成功通知不會被錯誤或重新整理誤認為尚未完成。

**Why this priority**: 管理員需要立即確認操作結果，尤其在成員清單較長或 Modal 關閉後，明確回饋能降低重複點擊與不確定感。

**Independent Test**: 成功完成角色、停用、重新啟用與醫療資料權限等各類異動，逐一確認左下角 Toast 的動作、目標與結果清楚；對拒絕或失敗的操作確認不出現成功 Toast。

**Acceptance Scenarios**:

1. **Given** 權限異動已成功保存，**When** 管理員回到權限管理清單，**Then** 左下角顯示成功 Toast，內容至少包含完成的動作與目標成員，且不顯示內部識別碼或敏感資料。
2. **Given** 權限異動被人數限制、授權檢查或資料衝突拒絕，**When** 系統回報結果，**Then** 不顯示成功 Toast，並讓管理員知道需重新檢視目前清單或修正條件。
3. **Given** 管理員連續完成多項異動，**When** 每項異動依序成功，**Then** 每項成功結果都可被辨識，不會把前一項動作錯誤套用到下一項目標。

### Edge Cases

- 系統只計算目前收容所內、角色為 `SHELTER_ADMIN` 且狀態為啟用中的 Membership；停用、過期或封存的管理員不計入啟用中人數，但仍保留查詢與稽核歷史。
- 只有一位啟用中的收容所管理員時，停用、降權、封存或其他會使其失去有效管理權的動作必須被拒絕。
- 已有兩位啟用中的收容所管理員時，新增、提升或重新啟用任何會形成第三位的操作必須被拒絕。
- 管理員開啟確認 Modal 後，目標成員可能先被其他操作者修改；提交時必須重新檢查最新狀態，避免以舊資料覆寫新資料。
- 兩個權限異動同時發生時，最終結果不得突破每個收容所一至兩位的管理員人數邊界，也不得留下只完成一半的異動。
- 管理員取消或關閉 Modal 後重新操作，不得沿用前一次的確認狀態或重複送出前一次異動。
- 權限異動失敗、網路中斷或重新整理時不得顯示成功 Toast；若實際結果不明，頁面應提示重新確認清單狀態。
- 成功 Toast 不得顯示密碼、醫療資料內容或僅讓一般管理員難以辨識的 UUID；應優先使用姓名與帳號。
- 收容所 A 的管理員只能調整收容所 A 範圍內的 Membership；不得因 Modal 或 Toast 內容查看或推測收容所 B 的資料。

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: 系統 MUST 以收容所為單位計算啟用中的 `SHELTER_ADMIN` Membership；不同收容所的管理員人數不得合併計算。
- **FR-002**: 系統 MUST 將每個收容所啟用中的 `SHELTER_ADMIN` 人數維持在至少一位、最多兩位。
- **FR-003**: 任何會新增啟用中 `SHELTER_ADMIN` 的建立、提升或重新啟用操作，MUST 在提交時重新確認上限；若目前已有兩位，MUST 拒絕操作並說明原因。
- **FR-004**: 任何會使啟用中的 `SHELTER_ADMIN` 減少的停用、降權或封存操作，MUST 在提交時重新確認下限；若目前只有一位，MUST 拒絕操作並說明至少須保留一位。
- **FR-005**: 人數上下限檢查、目標權限檢查與操作者授權檢查 MUST 以同一個完整結果完成；任一檢查失敗時不得只套用部分權限變更。
- **FR-006**: 系統 MUST 對可能同時發生的權限異動維持每個收容所一至兩位管理員的最終一致結果，不得因畫面上顯示的名額而直接信任過期狀態。
- **FR-007**: 既有成員的角色、啟用狀態、醫療資料權限或志工授權等有效權限調整，MUST 在實際提交前顯示確認 Modal；建立或提升為啟用中 `SHELTER_ADMIN` 的流程也 MUST 遵守同一項人數檢查。
- **FR-008**: 確認 Modal MUST 顯示目前收容所、目標成員姓名或帳號、目前權限／狀態、變更後權限／狀態，以及會影響的管理員人數或授權結果；不得以 UUID 作為唯一主要識別資訊。
- **FR-009**: 確認 Modal MUST 提供明確的確認與取消操作，並支援關閉與 Escape；取消、關閉或離開 Modal MUST 不得改變權限資料。
- **FR-010**: 系統 MUST 只在權限異動成功保存後於頁面左下角顯示成功 Toast；Toast MUST 明確描述完成的動作與目標成員，且不得包含密碼、醫療資料內容或不必要的內部識別碼。
- **FR-011**: 權限異動被拒絕、保存失敗或結果不明時，系統 MUST 不顯示成功 Toast，並提供可理解的錯誤或重新確認目前狀態的提示。
- **FR-012**: 每次成功或拒絕的權限異動 MUST 保留既有稽核要求，至少包含操作者、時間、目標 Membership、操作類型、變更前後狀態、結果與拒絕原因（如有）。
- **FR-013**: 權限管理與確認內容 MUST 遵守目前收容所的授權範圍；收容所管理員不得查看、修改或透過通知洩漏其他收容所資料。
- **FR-014**: 本功能 MUST 維持平台管理員角色與收容所 Membership 角色的獨立性；調整收容所管理員人數不得未經明確操作改變平台管理員權限。
- **FR-015**: 本功能 MUST 維持既有志工有效期間、已停用、已過期與已撤銷的狀態語意；重新啟用不得繞過志工授權流程，也不得把志工授權狀態誤顯示為帳號已恢復。
- **FR-016**: 不同權限異動的成功 Toast MUST 能各自對應到實際完成的操作與目標，避免連續操作時產生錯誤或重複的結果訊息。
- **FR-017**: 系統 MUST 使用 Membership 既有的 `access_version` 做確認後的樂觀並發控制；更新、封存或恢復請求若不是以 Modal 開啟時讀到的版本為基礎，MUST 拒絕寫入、不得部分修改，並要求操作者重新載入最新狀態。

### Key Entities _(include if feature involves data)_

- **收容所 Membership**：使用者與單一收容所的角色及啟用狀態關聯；其中啟用中的 `SHELTER_ADMIN` 數量受每個收容所一至兩位的治理規則限制。
- **權限調整確認**：管理員在提交權限異動前檢視的目標、前後權限、狀態與人數影響。
- **權限異動 Toast**：成功完成異動後提供給操作者的短暫結果通知，包含可辨識的動作與目標。
- **稽核紀錄**：記錄權限調整的操作者、時間、範圍、前後狀態、結果與拒絕原因，供後續追溯。

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 所有成功完成的收容所權限異動中，100% 的收容所啟用中的 `SHELTER_ADMIN` 數量都落在一至兩位之間。
- **SC-002**: 在只有一位啟用中管理員或已有兩位啟用中管理員的邊界測試中，100% 的違反下限或上限操作被拒絕，且既有權限與目標狀態不被部分修改。
- **SC-003**: 100% 的有效權限調整都必須先經操作者明確確認；取消、關閉或 Escape 後的測試案例不得產生權限資料變更。
- **SC-004**: 每次成功異動後，管理員在 2 秒內能在左下角看到 Toast，且 100% 的 Toast 能辨識完成的動作與目標成員，不含敏感資料。
- **SC-005**: 權限異動失敗或結果不明的測試案例中，成功 Toast 出現率為 0%，並且 100% 提供可理解的後續提示。
- **SC-006**: 成功與拒絕的權限異動稽核紀錄必要欄位覆蓋率達 100%，且可區分收容所範圍與實際操作結果。
- **SC-007**: 在桌面、平板與手機寬度的驗收中，100% 的確認 Modal 與左下角 Toast 不遮蔽主要資訊、沒有裁切或水平溢出，且鍵盤使用者可以完成確認或取消。
- **SC-008**: 使用包含管理員、工作人員、志工及停用歷史的標準測試資料時，至少 4/5 位管理者可在 30 秒內辨識目前管理員人數、異動後人數與本次 Toast 的完成動作。

## Assumptions

- 「至少一個、最多兩個」指每個收容所啟用中的 `SHELTER_ADMIN` Membership；平台管理員的人數政策另由既有平台治理規格管理。
- 停用、過期或封存的收容所管理員不計入啟用中人數，但其 User、Membership 歷史與稽核紀錄仍保留；若既有資料已低於一位，任何會進一步減少管理能力的操作仍應被拒絕。
- 確認 Modal 是單次明確確認，不要求第二位管理員共同批准；操作者身份與可調整範圍沿用現有授權規則。
- Toast 是成功結果的輕量通知；錯誤與人數限制拒絕仍以頁面或 Modal 內的可理解訊息呈現，不以成功 Toast 取代。
- 本功能不引入永久刪除 User，也不改變已封存成員的額外查詢路由；只補充收容所管理員人數與權限調整的確認及結果回饋。
- 時區維持既有台灣收容所的顯示規則，不在本功能重新設計或要求管理員修改時區。
- 所有重要權限異動仍須遵循最小權限、多收容所資料隔離與稽核可追溯原則。
