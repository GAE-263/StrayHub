# Feature Specification: 觀察詞彙管理介面資訊架構與可讀性優化

**Feature Branch**: `002-observation-vocabulary-ux`

**Created**: 2026-08-10

**Status**: Draft

**Input**: User description: 為 `/settings/observation-options` 建立以台灣繁體中文為主、依觀察類別分組、支援搜尋篩選與安全管理操作的觀察詞彙管理介面，降低長清單閱讀負擔並保留平台預設資料與歷史回報的可追溯性。

## Feature Overview

目前觀察詞彙管理頁面將約 13 個觀察類別與大量平台預設選項平鋪在同一份長清單中。收容所管理者必須同時辨識英文 stable code、英文顯示名稱、類別、來源與狀態，才能找到要維護的項目；一般工作人員與志工則容易被管理細節干擾。這會增加誤讀、誤改及停用錯誤選項的風險，也讓日後在手機回報流程中使用的詞彙不易理解。

本功能重新整理 `/settings/observation-options` 的資訊架構與互動規則，讓使用者先理解整體狀況，再按觀察類別逐步查看需要的選項。中文名稱是主要辨識資訊，stable code、來源、說明與最後修改資訊是次要資訊。平台預設選項與收容所自訂選項維持清楚的資料邊界；收容所管理者可以管理自己的自訂選項，但不能以此頁面改寫平台預設資料。

本規格遵循專案 constitution：

- **志工低摩擦**：詞彙的主要顯示名稱使用台灣繁體中文，並保留適合手機回報的短而清楚用語。
- **歷史追溯**：停用或封存只影響新的回報表單，不移除歷史回報；歷史內容保留當時的顯示名稱與 stable code 快照。
- **權限、隱私與稽核**：管理操作只限具備設定管理權限的使用者，所有變更保留操作者、時間、前後內容與收容所範圍。
- **多收容所資料隔離**：每個收容所只能讀取、建立與修改自己擁有的自訂選項，不能以網址、搜尋條件或其他入口取得其他收容所資料。
- **正體中文**：頁面、表單、狀態、提示、錯誤與空狀態均以台灣繁體中文為主要語言；stable code 等技術識別資訊維持英文。

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 先看懂收容所目前的觀察詞彙全貌（Priority: P1）

收容所管理者進入觀察詞彙頁面時，先看到觀察類別數量、啟用中的選項數量、收容所自訂選項數量，以及已停用或封存的選項數量。頁面同時以繁體中文說明平台預設與收容所自訂的差異，讓管理者不必先讀完整清單就能了解目前狀況。

**Why this priority**: 摘要與來源說明是降低長清單認知負擔、避免誤解資料所有權的基礎；若使用者一開始無法分辨哪些資料能管理，後續操作容易出錯。

**Independent Test**: 使用含 13 個類別、平台預設選項、自訂選項、停用選項與封存選項的收容所資料登入頁面，讓管理者在不展開任何類別的情況下回答四項摘要數量及平台預設／自訂差異；頁面只提供本收容所範圍的資料。

**Acceptance Scenarios**:

1. **Given** 收容所已有 13 個觀察類別及不同來源與狀態的選項，**When** 具備設定管理權限的使用者開啟頁面，**Then** 頂部顯示四項摘要數量，且數字與目前收容所完整資料一致。
2. **Given** 頁面已載入，**When** 使用者閱讀來源說明，**Then** 能以繁體中文理解「平台預設」是全平台提供、管理者不可直接改寫的基礎詞彙，「收容所自訂」是本收容所可維護的詞彙。
3. **Given** 頁面首次載入，**When** 使用者查看類別區域，**Then** 只看見類別摘要，不會直接展開全部選項。
4. **Given** 使用者套用搜尋或篩選，**When** 查看頂部摘要，**Then** 頂部摘要仍代表本收容所的完整總量；頁面另清楚顯示目前條件下的符合筆數，避免把篩選結果誤認為總量。

### User Story 2 - 依類別逐步找到需要維護的選項（Priority: P1）

收容所管理者可以展開或收合單一觀察類別。類別標題顯示啟用數量、自訂數量與停用／封存數量；展開後先顯示收容所自訂選項，再提供平台預設選項區段。每個選項以中文名稱為主，stable code、來源、說明與最後修改資訊為次要資訊。

**Why this priority**: 分組與漸進式揭露直接處理現有長清單問題，也讓管理者能先處理最可能需要修改的自訂內容。

**Independent Test**: 使用者不依賴管理細節欄位，只透過類別中文名稱、類別摘要與自訂選項優先順序，在展開一個類別後找到指定的自訂選項並辨識其狀態與來源。

**Acceptance Scenarios**:

1. **Given** 頁面有多個觀察類別，**When** 使用者查看類別列表，**Then** 顯示以下 13 個中文名稱及其次要英文 code：照護完成 `care_completion`、散步完成 `walk_completion`、進食 `feeding`、飲水 `water`、活動 `activity`、排尿 `urination`、排便 `defecation`、護食 `resource_guarding`、人際互動 `human_interaction`、動物互動 `animal_interaction`、情緒 `emotion`、散步 `walk`、外觀／特殊狀態 `appearance_special_status`。
2. **Given** 某類別含 4 個啟用選項、2 個收容所自訂選項及 1 個停用或封存選項，**When** 使用者查看類別標題，**Then** 能看到對應的啟用、自訂與停用／封存數量；計數的文字與顏色以外的方式均可辨識。
3. **Given** 某類別同時含平台預設與收容所自訂選項，**When** 使用者展開類別，**Then** 自訂區段先於平台預設區段顯示；平台預設區段可另行展開查看。
4. **Given** 使用者已展開一個類別，**When** 點選收合或另一個類別，**Then** 被收合的選項內容不再佔用閱讀空間，且目前操作不會改變選項資料或篩選條件。
5. **Given** 選項尚未被篩選隱藏，**When** 使用者閱讀選項項目，**Then** 首要文字是中文名稱；stable code、來源標籤、說明、狀態與最後修改資訊以次要層級呈現，不會搶過中文名稱。

### User Story 3 - 以搜尋與組合篩選快速定位選項（Priority: P1）

收容所管理者或一般工作人員可以使用中文名稱、英文 stable code 或說明搜尋觀察選項，並同時依觀察類別、狀態與來源篩選。搜尋與篩選結果仍依類別分組，讓使用者可以在大量資料中快速確認用途與管理範圍。

**Why this priority**: 即使有分組，既有平台預設選項仍可能很多；組合搜尋與篩選是管理者快速找到自訂選項、工作人員快速理解可用詞彙的必要操作。

**Independent Test**: 建立一組同類別、不同來源、不同狀態且名稱與說明部分相似的資料，驗證中文、stable code、說明搜尋，以及類別、狀態、來源的任意組合只回傳同時符合的結果。

**Acceptance Scenarios**:

1. **Given** 選項的中文名稱、stable code 或說明含有搜尋文字，**When** 使用者輸入該文字，**Then** 顯示符合任一搜尋欄位的選項；英文 stable code 搜尋不因大小寫差異而漏掉結果。
2. **Given** 使用者已輸入搜尋文字，**When** 再選擇一個觀察類別、狀態與來源，**Then** 結果同時符合搜尋文字、類別、狀態與來源條件，而不是以任一條件放寬結果。
3. **Given** 使用者選擇「啟用中」與「收容所自訂」，**When** 查看結果，**Then** 不顯示平台預設或停用／封存選項，且結果數量與畫面內容一致。
4. **Given** 搜尋或篩選沒有結果，**When** 使用者查看結果區，**Then** 顯示友善的繁體中文說明，並提供「清除搜尋與篩選」操作；清除後恢復完整摘要與類別列表。
5. **Given** 使用者只選擇來源或狀態篩選，**When** 查看結果，**Then** 類別仍以中文名稱分組，沒有符合結果的類別不會顯示空的選項列表。

### User Story 4 - 新增與修改收容所自訂觀察選項（Priority: P1）

具備設定管理權限的收容所管理者可以新增收容所自訂選項，或修改既有自訂選項的中文名稱、說明、排序與「是否需要補充說明」。新增與編輯表單要清楚說明每個欄位用途，並在輸入過程中提示空白、格式錯誤或重複 stable code。

**Why this priority**: 收容所需要把自己的照護語境轉成志工看得懂的詞彙；若無法安全地維護自訂選項，資訊架構優化仍不能完成管理價值。

**Independent Test**: 使用具備設定管理權限的帳號新增一個自訂選項、觸發必填與 stable code 驗證、成功儲存後再修改中文名稱、說明、排序及補充說明需求，確認只有本收容所資料被改變。

**Acceptance Scenarios**:

1. **Given** 使用者具備本收容所設定管理權限，**When** 點選「新增選項」，**Then** 表單至少顯示觀察類別、中文名稱、stable code、說明、排序與「是否需要補充說明」欄位，並以繁體中文說明必填與用途。
2. **Given** 使用者填寫合法的類別、中文名稱與未重複 stable code，**When** 儲存新增表單，**Then** 新選項以「收容所自訂」及「啟用中」顯示，並依所選類別與排序出現在自訂區段。
3. **Given** 使用者未填中文名稱、stable code，或只輸入空白，**When** 嘗試儲存，**Then** 在對應欄位顯示友善錯誤，保留其他已填內容，且不建立半成品選項。
4. **Given** stable code 含大寫、空白或不允許的符號，**When** 使用者輸入或離開欄位，**Then** 即時提示可接受的格式；格式未修正前不能儲存。
5. **Given** 目前收容所可見的完整有效詞彙範圍已有相同 stable code，**When** 使用者輸入該 code，**Then** 明確提示「目前收容所已有相同 stable code」，並阻止儲存；提示不得只顯示不易理解的技術錯誤。
6. **Given** 使用者編輯收容所自訂選項，**When** 修改中文名稱、說明、排序或是否需要補充說明並儲存，**Then** 後續新的回報表單使用更新後內容，且頁面顯示明確的繁體中文成功回饋。
7. **Given** 使用者查看平台預設選項，**When** 嘗試從本頁編輯，**Then** 不提供可修改 stable code、名稱、說明或來源的管理操作，並說明平台預設資料由平台統一維護。
8. **Given** 自訂選項尚未被任何歷史回報使用，**When** 具備權限的管理者需要修正 stable code，**Then** 可以依相同格式與唯一性規則修改；**Given** 選項已有歷史回報使用，**When** 管理者編輯該選項，**Then** stable code 鎖定為唯讀，避免破壞既有追溯關係。

### User Story 5 - 安全地排序、停用、恢復或封存選項（Priority: P1）

收容所管理者可以調整自訂選項在同一類別中的順序，並以清楚的確認流程停用、恢復或封存自訂選項。停用或封存只影響新的回報表單，不刪除歷史回報；系統不提供無提示的永久刪除。

**Why this priority**: 選項生命週期直接影響回報可用性與歷史資料完整性，是管理功能的主要風險控制。

**Independent Test**: 以已被歷史回報使用及未被使用的自訂選項各一個，測試排序、停用、恢復、封存與新回報表單可見性，並在歷史回報中確認原始名稱與 stable code 仍可追溯。

**Acceptance Scenarios**:

1. **Given** 同一類別有多個自訂選項，**When** 管理者調整排序並儲存，**Then** 新的管理介面與後續回報表單依更新後順序呈現，且平台預設的基礎順序不被收容所操作改寫。
2. **Given** 自訂選項目前為啟用中，**When** 管理者點選「停用」，**Then** 先顯示確認訊息：「停用後不會出現在新的回報表單，但歷史回報仍會保留。」使用者確認後才變更為「已停用」。
3. **Given** 管理者在停用確認視窗選擇取消，**When** 回到列表，**Then** 選項仍為啟用中，沒有產生狀態變更或誤導性的成功訊息。
4. **Given** 選項已停用或封存，**When** 管理者選擇「恢復」並確認，**Then** 選項回到啟用中、可出現在新的回報表單，並保留原有排序與歷史內容。
5. **Given** 選項已被歷史回報使用，**When** 使用者查看管理操作，**Then** 不提供永久刪除；可使用停用或封存替代，且頁面說明歷史回報仍會保留。
6. **Given** 選項已停用或封存，**When** 志工建立新的回報，**Then** 新表單不顯示該選項；**When** 工作人員查看使用過該選項的歷史回報，**Then** 仍能看到當時的觀察內容。

### User Story 6 - 在管理細節與快速閱讀之間切換（Priority: P2）

一般工作人員可以快速查看目前可使用的啟用中觀察詞彙，但看不到不必要的管理操作；收容所管理者在桌面版可以查看完整來源、狀態與管理操作。小尺寸螢幕上的詞彙名稱、狀態與操作不會互相擠壓，且所有主要操作可用鍵盤與螢幕閱讀器完成。

**Why this priority**: 同一份詞彙資料同時服務管理與現場理解；分離管理細節能降低一般工作人員與後續手機回報流程的負擔。

**Independent Test**: 分別用一般工作人員與管理者帳號，在桌面與手機寬度查看同一組資料，驗證可見內容、操作權限、文字可讀性、鍵盤順序及狀態辨識均符合角色與裝置情境。

**Acceptance Scenarios**:

1. **Given** 一般工作人員只有觀察詞彙查看權限，**When** 開啟詞彙頁面，**Then** 可快速查看啟用中的中文名稱與用途，但看不到新增、編輯、排序、停用或恢復按鈕。
2. **Given** 管理者使用桌面寬度，**When** 開啟一個類別，**Then** 可以在不反覆捲動整頁的情況下查看自訂與平台預設區段，並找到明確命名的管理按鈕。
3. **Given** 使用者以小尺寸螢幕查看頁面，**When** 讀取選項與操作，**Then** 介面改以卡片或可水平閱讀的簡化呈現；中文名稱、狀態與主要動作不被截斷或互相覆蓋。
4. **Given** 使用者只使用鍵盤，**When** 依序移動焦點、展開類別、套用篩選、開啟表單並送出，**Then** 焦點順序合理、目前位置清楚、所有可操作控制均可使用，且不需要依賴滑鼠拖曳。
5. **Given** 使用者使用螢幕閱讀器，**When** 閱讀類別、選項、狀態與錯誤，**Then** 能取得標題階層、展開／收合狀態、來源與狀態文字、欄位標籤及錯誤內容；狀態不只透過顏色辨識。

### User Story 7 - 只在正確收容所範圍內管理並留下稽核紀錄（Priority: P1）

具備設定管理權限的使用者只能管理目前所屬且已驗證的收容所。每次新增、修改、排序、停用、恢復或封存都保留操作者、時間、收容所、變更前後內容與操作結果；不同收容所即使有相同 stable code，也不得互相影響。

**Why this priority**: 觀察詞彙可被新回報表單使用，錯誤的跨收容所讀寫會造成資料污染與權限風險；租戶隔離與稽核是發布前不可省略的安全條件。

**Independent Test**: 建立 A、B 兩個收容所，為兩者建立相同 stable code 的自訂選項，讓 A 管理者嘗試以 A 的所有可用入口讀寫 B 的資料，再查閱稽核紀錄與兩所資料，確認隔離與追蹤完整。

**Acceptance Scenarios**:

1. **Given** 使用者只被授權管理收容所 A，**When** 查看頁面，**Then** 只顯示 A 的自訂選項與平台預設選項，不顯示 B 的自訂選項或可推測 B 存在的筆數。
2. **Given** A、B 各有一個相同 stable code 的自訂選項，**When** A 管理者修改或停用 A 的選項，**Then** B 的選項、可用狀態與排序完全不變。
3. **Given** 使用者以其他收容所的識別資訊、網址或搜尋條件嘗試讀寫，**When** 系統處理請求，**Then** 拒絕操作且不洩漏對方選項名稱、筆數、狀態或是否存在。
4. **Given** 具備設定管理權限的使用者完成任一項新增、修改、排序、停用、恢復或封存，**When** 儲存成功，**Then** 稽核紀錄包含操作者、時間、收容所、目標選項、操作類型、變更前內容、變更後內容與結果。

## 主要使用流程

### 流程一：首次進入與理解頁面

1. 使用者進入 `/settings/observation-options`，系統先確認身分、目前收容所範圍與查看或管理權限。
2. 頁面顯示標題「觀察詞彙」、一句用途說明、四項摘要卡，以及「平台預設／收容所自訂」差異說明。
3. 使用者看到搜尋與篩選工具，以及 13 個收合的觀察類別摘要。
4. 使用者展開需要的類別；自訂選項先出現，平台預設選項另以次要區段查看。

### 流程二：找到並編輯自訂選項

1. 使用者輸入中文名稱、stable code 或說明的關鍵字。
2. 使用者可再選擇類別、狀態與來源；結果只保留同時符合的資料。
3. 使用者展開結果中的類別，閱讀中文名稱與次要資訊，確認來源為「收容所自訂」。
4. 使用者選擇「編輯」，在表單修改中文名稱、說明、排序或是否需要補充說明。
5. 系統即時驗證必填、格式與唯一性；錯誤時保留輸入，成功時顯示明確回饋並更新列表與摘要。

### 流程三：新增收容所自訂選項

1. 管理者選擇「新增選項」。
2. 填寫觀察類別、中文名稱、stable code、說明、排序與是否需要補充說明。
3. 系統在輸入過程提示 stable code 格式與重複問題。
4. 儲存前顯示將建立為「收容所自訂／啟用中」的結果；儲存後回到原本的類別與篩選脈絡，並提供成功回饋。

### 流程四：停用、恢復或封存

1. 管理者在自訂選項上選擇「停用」、「恢復」或「封存」。
2. 停用／封存確認內容明確說明不會出現在新的回報表單、歷史回報仍會保留；使用者可取消。
3. 確認後，狀態、摘要數量、類別計數、可用的主要操作與新回報表單同步更新。
4. 歷史回報顯示原有的選項快照；管理列表保留當前狀態與最後修改者資訊。

### 流程五：一般工作人員快速閱讀

1. 一般工作人員進入可查看的詞彙頁面。
2. 頁面優先顯示啟用中的詞彙與中文說明，預設不顯示停用／封存項目。
3. 工作人員可用類別、搜尋文字與來源篩選理解目前可用的詞彙，但不會看到管理按鈕。

## 頁面資訊架構

### 1. 頁面入口與權限提示

- 頁面標題：`觀察詞彙`。
- 副標題：說明這些詞彙用於日常照護回報，並以非診斷性的現場觀察描述為主。
- 無管理權限但有查看權限者：顯示唯讀詞彙內容，不顯示管理按鈕。
- 無查看權限者：顯示「您沒有查看觀察詞彙的權限，請聯絡收容所管理者。」且不顯示任何資料摘要或資料筆數。

### 2. 頂部摘要區

摘要以四張易讀的資訊卡或等價結構呈現：

| 摘要項目 | 計算範圍 | 顯示目的 |
| --- | --- | --- |
| 觀察類別 | 本收容所可使用或可追溯的非封存類別 | 讓使用者理解詞彙的主題範圍 |
| 啟用中的選項 | 平台預設與收容所自訂的啟用中選項總數 | 了解目前可出現在新回報表單的選項量 |
| 收容所自訂選項 | 本收容所擁有的選項總數，包含停用與封存項目 | 了解管理者需要維護的範圍 |
| 已停用或封存 | 本收容所範圍內狀態為已停用或已封存的選項 | 了解歷史保留與清理狀況 |

摘要數量以目前收容所的完整資料計算，不因搜尋或篩選改變。篩選結果區另外顯示「目前符合條件：N 個選項」。

### 3. 資料來源說明

在摘要下方以繁體中文明確說明：

- **平台預設**：平台提供的共同基礎詞彙，收容所可以查看、搜尋與套用狀態篩選，但不能從本頁直接改寫其 stable code、中文名稱、說明或來源。
- **收容所自訂**：只屬於目前收容所的詞彙，具備設定管理權限的使用者可以新增、編輯、排序、停用、恢復或封存。
- 停用或封存不會刪除歷史回報；它只會影響新的回報表單是否顯示。

### 4. 搜尋與篩選區

- 搜尋框標籤：`搜尋觀察詞彙`。
- 搜尋提示：`可搜尋中文名稱、stable code 或說明`。
- 觀察類別篩選：`全部類別` 加上 13 個中文類別名稱，英文 code 為次要資訊。
- 狀態篩選：`全部`、`啟用中`、`已停用`、`已封存`。
- 來源篩選：`全部來源`、`平台預設`、`收容所自訂`。
- 同時使用時採「所有條件都符合」規則。
- 提供「清除搜尋與篩選」按鈕；清除後恢復完整結果、摘要與類別收合狀態。

### 5. 類別摘要與選項內容

每個類別是一個可展開／收合的內容區塊，依既有顯示順序呈現。類別標題包含：

- 中文類別名稱；
- 英文 code（次要文字）；
- 啟用中的選項數量；
- 收容所自訂選項數量；
- 已停用／已封存選項數量；
- 展開或收合狀態。

展開後依下列順序呈現：

1. 收容所自訂選項：啟用中優先，其次為已停用／已封存；同一狀態內依管理者設定的排序呈現。
2. 平台預設選項：啟用中優先，其次為已停用／已封存；平台原有順序不由收容所操作改寫。

每個選項的資訊層級如下：

- 主要資訊：中文名稱、狀態文字；
- 次要資訊：stable code、來源、說明、是否需要補充說明、最後修改時間與最後修改者；
- 管理操作：具備權限時顯示「編輯」、「停用」、「恢復」、「封存」等明確動詞；平台預設不顯示可修改操作；
- 狀態以文字、標籤或圖示與文字並用呈現，不以顏色作為唯一辨識方式。

### 6. 新增／編輯表單

表單標題清楚區分「新增收容所自訂選項」與「編輯收容所自訂選項」。欄位與說明如下：

| 欄位 | 必填 | 使用者可做的事 | 驗證與說明 |
| --- | --- | --- | --- |
| 觀察類別 | 是 | 選擇 13 個既有類別之一 | 新增時選定；本 MVP 不提供建立或刪除類別 |
| 中文名稱 | 是 | 輸入志工與工作人員看得懂的名稱 | 不可只有空白；儲存前必須通過長度與內容檢查 |
| stable code | 新增時是 | 建立可穩定識別選項的英文 code | 只接受小寫英文字母開頭，及小寫英文字母、數字、底線、句點；不得含空白或大寫；在目前收容所可見的完整有效詞彙範圍內不可重複 |
| 說明 | 否 | 補充觀察用途或使用情境 | 以簡短、非診斷性的台灣繁體中文為主 |
| 排序 | 是 | 調整同一類別中的自訂選項順序 | 只能輸入有效的非負整數或使用等價的上下移動操作 |
| 是否需要補充說明 | 是 | 選擇是／否 | 開啟時，新回報流程選用此詞彙後需提示補充文字 |

編輯已被歷史回報使用的選項時，stable code 為唯讀；若未被使用，仍須重新通過格式與唯一性驗證才可修改。表單中的錯誤必須靠近對應欄位，並在提交前可被鍵盤與螢幕閱讀器讀取。

### 7. 回饋與狀態區

- 載入中：顯示「正在載入觀察詞彙…」，摘要不顯示暫時的零值；載入失敗時提供「重新載入」。
- 儲存成功：顯示「觀察選項已儲存」或「觀察選項已停用／恢復／封存」，同時更新列表與摘要。
- 儲存失敗：保留使用者輸入、指出可處理的原因，並提供重試；不以成功狀態覆蓋現有資料。
- 沒有資料：顯示「目前沒有可顯示的觀察詞彙，請聯絡平台管理者確認平台預設資料。」；管理者仍可看到「新增選項」但不能繞過必要的類別資料。
- 沒有搜尋結果：顯示「找不到符合條件的觀察詞彙，請嘗試清除搜尋文字或放寬篩選條件。」及「清除搜尋與篩選」。
- 停用／封存確認：顯示選項中文名稱、目前狀態、作用範圍與「停用／封存後不會出現在新的回報表單，但歷史回報仍會保留。」並提供「取消」與「確認停用／確認封存」。

## Requirements _(mandatory)_

### Functional Requirements

#### 存取、權限與資料範圍

- **FR-001**: 系統 MUST 只允許已登入且具備觀察詞彙查看權限的使用者讀取頁面內容；未授權者不得看到摘要、類別數量或選項是否存在。
- **FR-002**: 系統 MUST 只允許具備目前收容所設定管理權限的使用者新增、修改、排序、停用、恢復或封存收容所自訂選項。
- **FR-003**: 系統 MUST 將每筆收容所自訂選項綁定至建立者所屬且已驗證的單一收容所；使用者提供的網址、選項識別或搜尋條件不得自行改變可存取的收容所範圍。
- **FR-004**: 系統 MUST 使平台預設選項在收容所管理畫面保持唯讀，至少不可由收容所管理者修改 stable code、中文名稱、說明、來源或平台基礎排序。
- **FR-005**: 系統 MUST 在所有權限判斷與資料讀寫上維持收容所隔離；A 收容所的使用者不得查看、搜尋、修改或推測 B 收容所的自訂選項資料。
- **FR-006**: 系統 MUST 讓沒有管理權限但有查看權限的一般工作人員使用唯讀模式，不顯示會造成誤操作的管理按鈕或管理表單。

#### 資訊架構與顯示

- **FR-007**: 系統 MUST 在頁面頂部顯示觀察類別數量、啟用中的選項數量、收容所自訂選項數量、已停用或封存選項數量，並以目前收容所完整資料計算。
- **FR-008**: 系統 MUST 顯示平台預設與收容所自訂的差異說明，以及停用／封存對新回報與歷史回報的影響。
- **FR-009**: 系統 MUST 使用指定的 13 個繁體中文觀察類別名稱作為主要名稱，英文 code 作為次要資訊，且既有類別 code 不得因介面改版而改名。
- **FR-010**: 系統 MUST 依觀察類別分組呈現選項，首次進入頁面時只顯示類別摘要，不直接展開所有選項。
- **FR-011**: 系統 MUST 在每個類別摘要顯示啟用、自訂及停用／封存數量；計數不得只依賴顏色或圖示辨識。
- **FR-012**: 系統 MUST 在類別展開後優先顯示收容所自訂選項，並把平台預設選項放在可另行展開查看的區段。
- **FR-013**: 系統 MUST 以中文名稱作為每個選項的主要資訊，將 stable code、來源、說明、狀態、是否需要補充說明、最後修改者與時間放在次要資訊層級。
- **FR-014**: 系統 MUST 以文字清楚顯示「平台預設」、「收容所自訂」、「啟用中」、「已停用」、「已封存」等來源與狀態，不以顏色作為唯一狀態辨識方式。
- **FR-015**: 系統 MUST 依既有平台順序顯示 13 個類別，並允許管理者只調整本收容所自訂選項在同一類別內的順序。

#### 搜尋與篩選

- **FR-016**: 系統 MUST 支援以中文名稱、英文 stable code 或說明搜尋，且英文搜尋不因大小寫差異而漏掉符合項目。
- **FR-017**: 系統 MUST 支援依觀察類別、狀態及來源篩選；狀態至少包含全部、啟用中、已停用、已封存，來源至少包含全部、平台預設、收容所自訂。
- **FR-018**: 系統 MUST 讓搜尋文字與類別、狀態、來源條件同時生效，結果只保留符合所有已選條件的選項。
- **FR-019**: 系統 MUST 在搜尋無結果時顯示繁體中文原因、目前使用中的條件與「清除搜尋與篩選」操作；清除後恢復完整結果。
- **FR-020**: 系統 MUST 在篩選結果中保留類別分組與必要的類別中文名稱；沒有符合選項的類別不得顯示空白清單。

#### 新增、編輯與排序

- **FR-021**: 系統 MUST 提供名稱為「新增選項」的明確入口，並在表單中要求觀察類別、中文名稱與 stable code。
- **FR-022**: 系統 MUST 允許具備權限的使用者修改收容所自訂選項的中文名稱、說明、排序與是否需要補充說明。
- **FR-023**: 系統 MUST 在新增與編輯時驗證中文名稱不可為空白、stable code 格式正確、目前收容所可見的完整有效詞彙範圍內 stable code 唯一、排序值有效，且在錯誤時指出可修正原因。
- **FR-024**: 系統 MUST 在 stable code 輸入或離開欄位時提供即時格式與重複提示，避免使用者到送出後才發現可預防的錯誤。
- **FR-025**: 系統 MUST 在 stable code 建立後維持其作為穩定識別資訊；未被歷史回報使用的自訂選項可依規則修改，已被使用的自訂選項必須鎖定 stable code。
- **FR-026**: 系統 MUST 在儲存成功後顯示明確的台灣繁體中文成功回饋，並同步更新選項、類別計數及摘要。
- **FR-027**: 系統 MUST 在儲存失敗時保留使用者已輸入的資料，顯示可理解的錯誤，並提供重試或返回操作；不得以空白表單覆蓋輸入。
- **FR-028**: 系統 MUST 在使用者重新開啟編輯表單時載入最新資料；若資料在編輯期間已被他人修改，必須提示資料已更新並要求使用者確認後再儲存。

#### 停用、恢復、封存與歷史資料

- **FR-029**: 系統 MUST 提供名稱清楚的「停用」操作，且停用前 MUST 以確認訊息說明「停用後不會出現在新的回報表單，但歷史回報仍會保留」。
- **FR-030**: 系統 MUST 提供「恢復」操作給已停用或已封存的收容所自訂選項，恢復前後均需顯示明確狀態與成功回饋。
- **FR-031**: 系統 MUST 提供可追蹤的「封存」狀態；封存選項不出現在新的回報表單，但可在管理頁面依狀態篩選並在歷史回報中追溯。
- **FR-032**: 系統 MUST 不提供無提示的永久刪除；對已被歷史回報使用的選項 MUST 禁止永久刪除，並引導使用者使用停用或封存。
- **FR-033**: 系統 MUST 只將啟用中的選項提供給新的回報表單；停用或封存不應阻止查看既有回報或重新解析歷史資料。
- **FR-034**: 系統 MUST 保留歷史回報建立當下的 stable code、中文名稱、觀察類別與必要說明快照；之後編輯、停用或封存不得重寫歷史回報原始顯示內容。
- **FR-035**: 系統 MUST 在歷史回報使用的選項目前已停用或封存時，仍顯示原始快照，並可附帶目前狀態提示，但不得把歷史內容顯示成新的名稱或新的選項。

#### 響應式、可及性與使用回饋

- **FR-036**: 系統 MUST 在桌面寬度提供適合管理效率的完整資訊層級與管理操作。
- **FR-037**: 系統 MUST 在小尺寸螢幕以卡片或可水平閱讀的簡化呈現，確保中文名稱、狀態、來源與主要操作不互相擠壓、截斷或覆蓋。
- **FR-038**: 系統 MUST 讓主要操作使用明確動詞，包括「新增選項」、「編輯」、「停用」、「恢復」、「封存」、「儲存」、「取消」與「清除搜尋與篩選」。
- **FR-039**: 系統 MUST 讓表單標籤、提示、錯誤、展開／收合狀態、來源與狀態可透過鍵盤操作及螢幕閱讀器理解；焦點不能在開啟或關閉表單後遺失。
- **FR-040**: 系統 MUST 以文字或文字加圖示呈現狀態、錯誤與成功，不得只依靠顏色、位置或形狀傳達必要意義。
- **FR-041**: 系統 MUST 在載入、載入失敗、沒有資料、搜尋無結果、儲存失敗與權限不足時提供對應的繁體中文說明及可採取的下一步。

#### 權限稽核與變更追蹤

- **FR-042**: 系統 MUST 為每一次新增、修改、排序、停用、恢復及封存保留操作者、操作時間、目前收容所、目標選項、操作類型、變更前內容、變更後內容與結果。
- **FR-043**: 系統 MUST 讓稽核內容能辨識 stable code、中文名稱、說明、排序、是否需要補充說明及狀態的變更；若某欄位未變更，仍不得被誤記為已變更。
- **FR-044**: 系統 MUST 讓平台預設選項的來源與收容所自訂選項的來源在列表、表單與稽核資訊中保持可區分。
- **FR-045**: 系統 MUST 確保稽核紀錄屬於正確的收容所範圍；收容所管理者只能查看被授權範圍的相關紀錄。
- **FR-046**: 系統 MUST 在管理操作成功回饋中提供可理解的變更結果，但不得在一般工作人員畫面洩漏不必要的管理或稽核細節。

## 主要驗收情境總表

下列情境是跨使用者故事的必要驗收基準，應以可觀察的畫面、角色行為與歷史資料結果驗證：

1. 首次進入頁面只顯示類別摘要，且四項頂部摘要數量正確。
2. 類別以「照護完成、散步完成、進食、飲水、活動、排尿、排便、護食、人際互動、動物互動、情緒、散步、外觀／特殊狀態」顯示，英文 code 為次要資訊。
3. 展開類別後，收容所自訂選項先於平台預設選項；平台預設區段可另行查看。
4. 搜尋中文名稱、stable code 或說明均能找到對應選項，且英文搜尋不受大小寫影響。
5. 同時使用搜尋、類別、狀態與來源篩選時，結果只符合所有條件。
6. 搜尋無結果時顯示繁體中文空狀態與清除操作，清除後恢復完整列表。
7. 一般工作人員可讀取啟用中的詞彙但看不到管理按鈕；管理者可看到管理操作。
8. 新增自訂選項時，空白名稱、非法 stable code、重複 stable code 與無效排序均被阻止並給出欄位級提示。
9. 新增成功後顯示「收容所自訂／啟用中」，並依所選類別與排序出現。
10. 編輯自訂選項的名稱、說明、排序與補充說明需求後，新的回報表單使用更新後內容。
11. 平台預設選項不能從此頁改寫 stable code、名稱、說明、來源或平台基礎排序。
12. 停用前會顯示歷史保留與新表單排除說明；取消不產生任何變更。
13. 停用後的新回報表單不顯示該選項，歷史回報仍顯示原始快照。
14. 已停用或封存的自訂選項可恢復；恢復後再次出現在新回報表單。
15. 已被歷史回報使用的選項沒有永久刪除操作，且 stable code 不可變更。
16. 在 320px 左右的小尺寸螢幕上，主要文字、狀態與按鈕不重疊或被截斷。
17. 只使用鍵盤可完成搜尋、展開、編輯、驗證、儲存、取消與狀態變更確認。
18. 使用螢幕閱讀器可辨識標題、類別、選項名稱、來源、狀態、錯誤及展開／收合狀態。
19. A、B 收容所各有相同 stable code 時，A 的管理操作不會改變 B 的資料，也不會洩漏 B 的存在。
20. 每次新增、修改、排序、停用、恢復及封存都能查到操作者、時間、收容所與前後變更內容。

## 空狀態、錯誤狀態、載入狀態與確認情境

### 空狀態

- **沒有任何可顯示資料**：顯示目前沒有可顯示的觀察詞彙、可能原因與聯絡平台管理者的下一步；不得顯示四張誤導性的零值摘要。
- **沒有自訂選項**：類別仍顯示平台預設選項數量，並在自訂區段顯示「目前尚無收容所自訂選項」及「新增選項」。
- **沒有符合搜尋結果**：說明是「找不到符合條件的觀察詞彙」，列出目前搜尋／篩選條件的摘要，提供「清除搜尋與篩選」。
- **一般工作人員查看**：預設隱藏停用／封存項目，若啟用中沒有結果，說明目前沒有可用詞彙，而不是暗示資料不存在。

### 錯誤狀態

- **權限不足**：不顯示任何受保護資料；以繁體中文說明需要查看或設定管理權限。
- **載入失敗**：保留頁面標題與安全的錯誤說明，提供「重新載入」，不把載入失敗當成空資料。
- **欄位驗證失敗**：錯誤靠近欄位，說明修正方式，保留其他輸入，且可被鍵盤與螢幕閱讀器讀取。
- **stable code 重複**：指出重複發生在目前收容所可見的詞彙範圍，提供修改 code 的建議，不清空表單。
- **儲存時資料已更新**：提示「此選項已被其他人更新，請重新確認最新內容」，保留使用者草稿，不能悄悄覆蓋他人變更。
- **操作失敗**：說明狀態沒有變更，提供重試；不顯示與實際結果不符的成功訊息。

### 載入狀態

- 初次進入、重新載入、套用條件與儲存後重新整理時，顯示清楚的載入中狀態。
- 載入中不可讓使用者誤以為所有摘要都是零或所有類別沒有選項。
- 若重新載入失敗，保留先前已可靠顯示的內容並標示資料可能尚未更新；若沒有先前內容，顯示完整錯誤空間。

### 停用、恢復與封存確認

- 停用確認至少包含：選項中文名稱、目前狀態、執行後狀態、停止出現在新回報表單、歷史回報保留，以及「取消／確認停用」兩個清楚動作。
- 封存確認至少包含：選項中文名稱、封存後不出現在新回報表單、歷史回報仍可查詢，以及「取消／確認封存」兩個清楚動作。
- 恢復確認至少包含：選項將重新出現在新回報表單、原有 stable code 與歷史資料不變，以及「取消／確認恢復」兩個清楚動作。
- 使用者取消任何確認時，頁面不得改變狀態、排序、摘要或稽核內容。

## 對既有平台預設選項與歷史回報資料的相容性要求

- 既有 13 個觀察類別及其 code 必須原樣保留，不能因頁面中文化而重新命名或建立會造成重複的類別。
- 既有平台預設 stable code（例如 `care_completion.completed`、`feeding.not_observed`、`appearance.changed`）必須可繼續被新的管理介面辨識、搜尋與顯示。
- 既有平台預設選項不得因本次介面優化而被複製成收容所自訂選項、重設順序、改變來源或意外停用。
- 已存在於新回報流程的啟用中選項，改版後仍必須能在相同觀察類別中提供給新的回報表單；停用或封存項目只從新表單排除。
- 歷史回報的原始觀察值、stable code、中文名稱、類別、建立時間與回報者不得因編輯、停用、恢復、封存或重新整理頁面而消失或被新名稱取代。
- 若既有歷史回報已有顯示快照，管理介面與歷史檢視 MUST 優先使用當時快照；若既有資料只有 stable code，系統仍 MUST 能顯示 stable code，並以不誤導歷史語意的方式標示目前或原始名稱來源。
- 收容所自訂選項的 stable code 變更必須只在沒有歷史使用時允許；一旦被使用即固定，避免新的名稱或 code 回溯改寫舊回報。
- 平台預設選項與收容所自訂選項必須以來源區分；即使兩者名稱或 stable code 相同，也不得混合計入彼此的管理範圍。
- 本功能不得刪除、覆寫或重新建立現有照護回報、原始文字、照片、觀察答案、人工修正或其歷史稽核紀錄。
- 後續手機回報流程讀取的啟用中詞彙，必須使用與管理介面相同的中文名稱、說明、排序與「是否需要補充說明」設定；管理頁面的資訊架構改版不得要求志工重新理解英文 stable code。

## Key Entities _(include if feature involves data)_

- **觀察類別**：代表一組相關照護觀察主題，包含中文名稱、英文 code、顯示順序與可見狀態；本功能使用既有 13 個類別，不在 MVP 中新增或刪除類別。
- **觀察選項**：可被選入照護回報的單一詞彙，包含 stable code、中文名稱、說明、所屬類別、來源、狀態、順序、是否需要補充說明與最後修改資訊。
- **平台預設選項**：平台共同提供的基礎觀察選項，來源固定、由收容所管理者唯讀查看，供各收容所在啟用狀態下使用。
- **收容所自訂選項**：只屬於一個收容所的自訂觀察選項，具備權限的收容所管理者可維護其可編輯內容與生命週期。
- **觀察選項歷史快照**：在回報建立時保存的 stable code、中文名稱、類別及必要說明，確保日後即使詞彙被改名、停用或封存，歷史內容仍能以當時語意呈現。
- **觀察詞彙變更稽核紀錄**：記錄新增、修改、排序、停用、恢復與封存的操作者、時間、收容所、前後內容、操作類型與結果。

## MVP 範圍

### 本次包含

- `/settings/observation-options` 的繁體中文資訊架構重整與可讀性優化。
- 四項頂部摘要、平台預設／收容所自訂差異說明，以及 13 個既有觀察類別的中文化顯示。
- 依類別分組、首次收合、類別計數、自訂優先與平台預設另行查看。
- 中文名稱、stable code、說明的搜尋，以及類別、狀態、來源的可組合篩選。
- 收容所自訂選項的新增、編輯、排序、停用、恢復與封存；包含即時驗證、友善錯誤與成功回饋。
- 平台預設選項唯讀、stable code 唯一性與格式驗證、已使用選項不可永久刪除。
- 載入、空狀態、錯誤狀態、停用／封存確認與資料更新衝突提示。
- 一般工作人員的唯讀快速查看、桌面管理情境、小尺寸螢幕、鍵盤與螢幕閱讀器支援。
- 收容所權限隔離、平台預設／自訂來源區分、所有管理變更的稽核，以及歷史回報顯示快照相容性。

### 本次不包含

- 建立、刪除、合併或重新命名觀察類別。
- 從收容所管理畫面編輯平台預設選項；平台共同詞彙的治理流程另立規格。
- 永久刪除任何觀察選項、批次刪除或以刪除取代停用／封存。
- 批次匯入、匯出、跨收容所複製或共享自訂詞彙。
- 批次排序、批次停用、批次恢復或批次封存操作。
- 重新設計完整手機回報表單、LINE Bot、LIFF 或其他輸入通道；本功能只要求詞彙設定能被後續回報流程正確使用。
- 詞彙的多語言翻譯、個別志工的詞彙版本、詞彙使用率分析或自動建議。
- 修改既有歷史回報的原始答案、照片、心得、人工修正或顯示快照內容。

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 至少 90% 的收容所管理者測試者能在首次進入頁面 30 秒內正確說出四項摘要數量及平台預設／收容所自訂的差異，不需要展開全部類別。
- **SC-002**: 至少 90% 的管理者測試者能在 45 秒內，使用中文名稱、stable code 或說明搜尋並找到指定的收容所自訂選項，且不需瀏覽超過 2 個無關類別。
- **SC-003**: 至少 90% 的具備管理權限測試者能在 2 分鐘內完成一個自訂選項的新增或編輯；測試過程中不得發生未說明的驗證錯誤或成功後資料消失。
- **SC-004**: 在至少 20 筆混合來源與狀態的測試資料中，100% 的測試者能以文字或標籤正確分辨平台預設、收容所自訂、啟用中、已停用與已封存，不必依賴顏色判讀。
- **SC-005**: 至少 90% 的測試者在停用確認前能說出「不會出現在新的回報表單，但歷史回報仍會保留」；取消確認後 100% 的測試案例不得產生狀態變更。
- **SC-006**: 在 320px 左右寬度與常見桌面寬度下，100% 的主要中文名稱、狀態、來源與主要按鈕可讀且不互相重疊或截斷；至少 90% 的手機情境測試者能在 60 秒內找到指定啟用詞彙。
- **SC-007**: 至少 90% 的鍵盤與螢幕閱讀器可及性測試流程能完成搜尋、展開、開啟表單、修正錯誤、取消及儲存；所有必要錯誤訊息都能被讀取。
- **SC-008**: 100% 的新增、修改、排序、停用、恢復與封存驗收案例都能查到正確操作者、時間、收容所、變更前後內容與結果；任何失敗操作不得產生成功稽核紀錄。
- **SC-009**: 100% 的既有平台預設選項與歷史回報回歸案例能在改版後被正確辨識；歷史回報原始 stable code、中文名稱與類別快照不得改變。
- **SC-010**: 在約 13 個類別與 500 個觀察選項的代表性資料量下，使用者在一般網路條件下能於 2 秒內看到可理解的頁面摘要或載入中狀態，搜尋或篩選操作在 2 秒內顯示結果或明確錯誤。
- **SC-011**: A、B 兩個收容所的 100% 隔離測試中，A 的使用者不能取得、修改或透過結果筆數推測 B 的自訂選項；A 的變更不會改變 B 的資料。
- **SC-012**: 上線後 30 天內，與觀察詞彙相關的「找不到自訂選項」、「不知道哪些可以修改」或「停用後歷史資料消失」支援問題，相較改版前基準至少下降 30%。

## Assumptions

- 現有身分驗證、目前收容所範圍與「設定管理權限」可供本功能沿用；若現有角色名稱不同，規劃階段應以同等權限語意對應，不擴大一般工作人員的管理能力。
- 目前平台已有 13 個既有觀察類別，類別建立、刪除與平台治理不在本功能；頁面以既有資料作為唯一類別來源。
- 現有平台預設選項與既有歷史回報的 stable code 需要被保留；允許既有 code 中使用底線與句點，以相容目前的回報語彙。
- 「封存」代表保留供歷史追溯但不提供給新回報的狀態；本 MVP 不提供任何永久刪除，因此恢復也不會抹除歷史稽核或快照。
- 收容所自訂 stable code 沿用現行規則，在目前收容所可見的完整有效詞彙範圍內唯一；平台預設與自訂不得互相重複。這保留既有回報 code 的穩定辨識方式，也不因介面改版改變既有有效資料的唯一性。
- 收容所管理者以桌面版為主要管理情境；一般工作人員與志工的手機使用情境以閱讀詞彙與後續回報可用性為主，不要求在手機上完成完整管理工作。
- 中文名稱、說明與「是否需要補充說明」的設定會被後續照護回報流程讀取；本規格不重新定義回報流程的問答順序或表單版面。
- 現有歷史資料若已有觀察快照，應直接沿用；若只有 stable code，規劃階段需提出不誤導歷史語意的補強方案，但不得以目前名稱無聲覆寫舊資料。
- 摘要與可見項目均以目前使用者已驗證的單一收容所範圍計算；平台管理員若需要跨收容所治理，應透過既有且可稽核的平台管理權限，不在一般收容所管理畫面放寬隔離。
- 一般網路條件與代表性資料量的速度目標是使用者可感知的驗收門檻，不指定任何技術實作方式。
